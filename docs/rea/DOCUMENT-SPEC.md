# Project document lifecycle and JSON contract

This specification follows the original ARM64 application's project file parse and save routes. It covers the project-level document contract and record defaults; note/chord serialization internals are outside scope. These are static findings from the installed executable, not runtime file captures.

## Open and save flow

The file-open adapter checks the supplied path with `_access` and `_stat`, rejects a directory, then passes the path to `FUN_1000135c8`. That function reads and parses the file, initializes a default project object, applies recognized project keys, then sends the parsed result through an application callback. The original artifact contains strings “Open Klimper Project” and “Import Klimper Project”, but the string inventory alone does not establish either string's UI placement or action target. A missing or unreadable path follows the default-object path; malformed JSON and field conversion errors can throw from the parser helpers, and the full UI error presentation was not followed.

### Import boundary and failure policy

The retained open-adapter/parser evidence is not connected to the artifact's “Import Klimper Project” string. No active menu association, importer callback, source-format dispatch, merge/replace mutation, track-ID collision handling, or import warning path is established. Treat `.klp` open as the bounded route described above and leave the meaning/action of the Import-labeled string unresolved.

For the bounded parser path, missing/unreadable input takes the default-object branch, while malformed JSON or a wrong required field kind can propagate an exception from a lower-level parser/helper. The evidence does not show whether the caller catches those exceptions, whether a partially initialized model can be delivered, or what alert/log/recovery the user sees. Missing required object keys use `map::at` and therefore fail rather than substituting constructor defaults. These facts define observed lower-level branches only; they do not specify the complete user-facing error contract.

The save adapter obtains the current model snapshot, invokes `FUN_10000b590` to build a JSON object, then serializes that object to text and passes it through the save callback. The writer adds the keys below; `ui_state` is included only when the save-state flag at `param_3 + 0x10` is nonzero. The nearby UI distinguishes “Save Klimper Project” and “Save Klimper Project as...”, and the file chooser is initialized with a `*.klp` filter. Filter enforcement is not established. This does not prove autosave, atomic replacement, or recovery behavior.

The observed top-level keys written are:

```text
name, scale, bpm, tracks, sections, chord_track,
looping: { _start, _end }, [ui_state]
```

The parser reads `name`, `scale`, `bpm`, `tracks`, `sections`, `chord_track`, `looping._start`, `looping._end`, and optional `ui_state`. The `_start` and `_end` members are children of the `looping` object, not root-level fields. The root `scale` key is required by lookup but its value is nullable: the writer emits JSON null when the project has no scale value, and the parser's optional-scale reader treats a non-object value as absent. It does not read or write a project `version` key in this path, and no version-based migration branch was found here. This is a bounded statement about these parser/writer functions, not proof that every import/export path lacks version metadata.

## Defaults and field behavior

`FUN_100010fec` initializes a project-like default record with BPM `120`, a floating-point `0.9` value, an empty loop range, false state, and an instrument string held in static data. This is the starting object for the file parser, but it does **not** mean required file fields may be omitted: the parser accesses required keys with a map lookup that throws when a key is missing. The observed default scale is C Major (see [PROJECT-MODEL.md](PROJECT-MODEL.md)); exact default instrument ID remains unresolved.

Track parsing requires the top-level `tracks` value to be an array; a missing or different-type value takes an exception path. For each array entry it initializes a record (`New Track`, volume `0.9`, pan `0`, mute/solo false, instrument string from static data), then reads the serialized `id`, `name`, `volume`, `pan`, `mute`, `solo`, and `instrument` keys. Because those lookups use the required-key accessor, the constructor values are not missing-field fallbacks for these keys. It allocates a fresh sequential ID candidate before reading `id`, so an explicit serialized ID replaces that candidate. Track parsing is in `FUN_1000135c8`, Evidence `ev_51fc7897a0a916450e6a1bb627f8a9ef221495dc32df1831f46329a95926202a`; the add-track constructor confirms the new-track label and `.9` initialization in `ev_eb6dda84aef8cb5c8886c19484a1fc1e18e870f8d58e5a532da24328abce049f`.

The chord-track object has `volume`, `pan`, `mute`, `solo`, and `instrument` fields. The `looping` object has `_start` and `_end` numeric fields. The writer converts internal loop start/end to JSON numeric values by dividing by `10368.0`; the parser multiplies those values by `10368.0` to reconstruct internal values. This inverse pair is directly visible in the writer/parser (`ev_7607806451f319706b04142bcb3dabf7bcb5110d567833674b0997579d97184`, `ev_51fc7897a0a916450e6a1bb627f8a9ef221495dc32df1831f46329a95926202a`).

## Typed field readers and failure cases

The parser's map lookup helper is `FUN_100016bdc`. For a JSON object it uses `map::at`, so a missing required member takes the key-not-found exception path. Typed scalar and array readers enforce accepted JSON value kinds and throw on other kinds; the nullable scale adapter and generic `ui_state` copier are explicit exceptions. This is not a permissive “fill every missing or malformed member from defaults” loader. Unknown object members are not forwarded into the reconstructed model, and the writer only emits the recognized shape above. Thus unknown top-level keys (including `version` on this path) are not migration inputs and are not round-tripped.

The matrix distinguishes required keys from nullable values: project and section writers always create a `scale` member, using JSON null when no scale value/override is stored. The parser still requires each member; its optional-scale reader parses an object and clears the optional value for non-object JSON values. The parser deep-copies an existing `ui_state` JSON value without imposing a scalar type. The save writer emits it only when the save-state flag is enabled.

Derived examples (not runtime results): the note leaf `{ "position": 1.5, "length": 0.25, "pitch": 61, "velocity": 0.8 }` converts position and length to `15552` and `2592` internal units, respectively. Boolean `velocity: true` becomes `1.0`; `pitch: 61.8` is stored through the unsigned integer conversion (fraction discarded for representable positive input). A note with `position: "1"`, `pitch: "60"`, or missing `velocity` fails its required typed lookup/conversion instead of silently defaulting. A boolean `position`, string `velocity`, or object-valued `tracks` also fails the observed reader's accepted-kind checks. These are derived parser outcomes, not runtime tests. A root `scale: {root: 0, name: "C Major", steps: [...]}` is not the observed shape: the reader expects `{root, type: {name, steps}}`.

## Implementation contract and limits

For an implementation that aims to read/write this document shape:

1. Initialize the default project state before applying parsed values.
2. Require `tracks` to be an array on this observed parse route; do not silently reinterpret another JSON type as an empty array.
3. Preserve top-level `ui_state` only when present, and emit it only on the writer's enabled state-save path.
4. Keep `looping._start` and `looping._end` as JSON numbers and apply the observed `10368` scale conversion at the project boundary.
5. Do not invent a `version` field or migration policy from this evidence.

The default scale is identified as C Major, but the exact default instrument identifier remains unresolved. This work establishes the listed reader conversions and failure cases; it does not enumerate every malformed field or conversion boundary. Extension enforcement, the import-versus-open distinction, and atomicity/error recovery remain unresolved. The writer's internal field coverage does not establish lossless round-trip behavior for unknown keys; this path rebuilds a recognized JSON object rather than retaining arbitrary source members.
