# Section timing and transform evidence

This note deepens the static section and note evidence for the Klimper 2.4 ARM64 executable. It uses Ghidra 12.1.4 through REA on the thin binary whose SHA-256 is `3f26469013c1d3ac1cde475d851641da312c3100aa5ad452fdb6ebc737476d41`. Pseudocode below is decompiler output; no app execution or `.klp` sample was used. New focused records are in [`rea-section-evidence.json`](../../research/rea-section-evidence.json); the earlier serializer and reader records remain in [`rea-project-evidence.json`](../../research/rea-project-evidence.json).

## Observed representation

- The section serializer at `0x10000f788` emits each section's `length` as its internal signed integer divided by `10368.0`. It recursively serializes nested sections or the alternate clip payload, selected from an internal tag. The serializer reads the section length from byte offset `0x20` in the native record. Evidence: `ev_b45d766071d21a280614a368efd50ffa2d6016291f4abc49b5e7e4ee1c9fe465`.
- A section-construction routine at `0x1000188a8` initializes the name to `New Section`, zeroes the record field at `+0x20`, and assigns an incrementing identifier at `+0xa0`. The serializer independently reads `+0x20` as section length, so the default section length is derived to be zero. It also selects a value from a global array using `rand()`; the array's contents and semantic meaning were not established. Evidence: `ev_5ba2233bae30f14b7ac822fbe9bbfe722e25febed0bd8f9442e4df999c94df23`; the exact `New Section` string reference is `ev_08d65dd1a1d78c4685e793576d6ff0b7541c0565298f5b590e6abb7386e42e79`.
- In one append path, `0x100048e0c` constructs this default section and appends it to a vector. The caller's intent is unresolved, so this proves the initialization and append sequence only; it does not establish which UI command invokes it or how other section-creation paths behave. Evidence: `ev_6dd173e02fa334ad41462b6279c02f996252b950d0578594cdc067bd081bd52a`; caller coverage for the constructor is in `ev_5ba2233bae30f14b7ac822fbe9bbfe722e25febed0bd8f9442e4df999c94df23`.
- Notes serialize `position` and `length` using the same `/ 10368.0` conversion, and serialize `pitch` as an integer cast from the internal note field. The project reader multiplies JSON `_start` and `_end` by `10368.0`. Chord and section lengths use that same factor. This proves a common storage/JSON conversion, not that the unit is beats or quarter notes. Evidence: note `ev_5ae6f6a575bd2aa6e6d31667e01c8a481f15e61287fb56a3d26062a464c709c0`; reader `ev_59912403cd72e51b56ac3bbabc9f238374881e2b80b8fa185d909f3d71fd23a6`; chord `ev_28a789c59da99977d9baa06b2a8530d1be5c45d7a5c5018a9a7252d627f00f7b`.
- Chord items persist a duration but the inspected chord serializer emits no separate position field. Note arrays persist per-note position and length under `clipByTrack`. This is a shape observation only; it does not prove whether chord positions are derived from ordering or stored elsewhere. Evidence: `ev_28a789c59da99977d9baa06b2a8530d1be5c45d7a5c5018a9a7252d627f00f7b`, `ev_b45d766071d21a280614a368efd50ffa2d6016291f4abc49b5e7e4ee1c9fe465`.

## UI text and bounded meaning

The binary contains the tooltip “Select the grid width for snapping notes, chords, and sections lengths,” the label “Moves left by an eigth note,” and “Transposes up by a half step.” These are observed UI strings, not verified action handlers or arithmetic. Evidence: `ev_865249cb6fea8cdd4d1d5ea2d701e67aa252a31ac209cd250af4a710b411ab9e`, `ev_01983e2b1779561100198979e5393274f8cf3e68c4954f50dce39790234773fa`, and `ev_f8daa0d2758d517e0ad704fa10d3fd7cbecc54e4c2d40072ff1497e80822d2f7`. The “eigth” spelling is present in the target string.

The binary also contains “Wrap In New Section.” This label establishes that the UI presents this operation, but its static reference did not resolve to a handler in this pass. Evidence: `ev_f11ef4f8a41f637a5f89cdc9a20dbbbeee07717c3bf641067a436d413c4d1862`.

## Transform questions still open

- **Timing unit and origin:** `10368` is only a scale factor. No inspected function proves ticks per beat, bar length, time signature, rounding policy, or whether note positions are section-relative or song-relative.
- **Resize:** no observed editor handler proves whether changing a section length shifts later siblings, clips notes, preserves absolute positions, or changes nested section durations. The serializer and constructor do not answer this.
- **Move, wrap, and insert:** section hierarchy and UI labels are observed; the target's operation handlers were not resolved to complete data transformations. Do not implement a presumed descendant offset rule from these findings.
- **Pitch:** a note's stored pitch is an integer, but this pass does not prove MIDI numbering, range, octave convention, or the actual arithmetic behind the half-step/octave commands. The labels alone do not establish these.
- **Default length:** a specific `New Section` initializer yields internal length zero, but it remains unknown whether all creation commands use it unchanged, whether a later command assigns a duration, or whether the UI immediately normalizes it.

Static evidence supports matching the JSON scaling and default record initialization. It does not yet support claiming parity for drag/resize/move/duplicate behavior or pitch conventions.

## Consolidated native model and parity contract

This section supersedes the earlier “move/wrap unresolved” wording only where later command-history and normalization evidence closes the question. It does not turn static call paths into runtime observations. The added focused records are in [`rea-section-model-completion-evidence.json`](../../research/rea-section-model-completion-evidence.json) (110 records; same ARM64 SHA-256 and Ghidra profile).

### Model that the implementation must represent

The native section collection is ordered and recursive. A section is a fixed-size `0xa8`-byte record. Its duration is the signed integer at `+0x20`; its content variant is the integer tag at `+0x98`. Tag `0` means nested section records, and tag `1` means the alternate clip payload. Paths are integer index vectors: each component indexes the current sibling list, and additional components descend through a section-valued record. A deeper path through a non-section record throws. This is a structural coordinate system, separate from musical time. Evidence: `ev_ce28543e00ee9f3e5dad91359771a2596d192587e00128d5d6914ebed562f4f4`, `ev_40a555538c64dd2a5dea9705f77f0e2d70134a2cbeb0a44fff02aedd292e478f`.

Section sibling placement is represented by list order and path indices; the serializer emits the section length as `+0x20 / 10368` and recursively emits the content variant. It does not emit a section start field in the inspected section schema. The recursive range-query visitor confirms sequential placement: it advances by each preceding sibling length and converts child-local note positions to song-relative positions at each nesting level. Chord starts are sequenced by summing earlier chord durations inside the containing section. Native JSON time numbers are multiplied by four in the clone's quarter-beat projection. The importer follows these rules; if a sibling length is missing or invalid, it preserves the raw subtree and omits later siblings whose absolute starts can no longer be derived. Mixed non-object nested arrays stay opaque and are not projected. Evidence: recursive visitor `ev_f15c55cf3db04491f734c204a5b540233ecf6949374761becb798ce8ad2d319b`, clip visitor `ev_d02191b5101a11694d9e6a88fbf7c4b509a4a6f855729cb0ae0f6437b59e124b`, and [`rea-section-recursive-position-evidence-2026-10-16.json`](../../research/rea-section-recursive-position-evidence-2026-10-16.json).

### Wrap command and history behavior

The RTTI-named `wrap_in_new_section` command is a real `Command<Song>` implementation. The command stack dispatches its `+0x10` vtable slot for execute (`FUN_100049a28`), `+0x18` for undo (`FUN_10004a864`), and `+0x20` for redo (`FUN_10004a894`). Undo reinserts complete saved `0xa8`-byte records at their saved paths. Redo reconstructs sibling storage around each saved range and restores the saved nested-section vector or alternate payload. The wrapper therefore needs reversible subtree/path snapshots; recreating inverse transforms from current state would not preserve the native full-record restoration behavior. ### What this means for the flat prototype

The current prototype still displays and edits `Song.sections` as flat `{id, name, start, duration}` ranges. `transformSection` finds contained notes/chords by absolute start, scales their positions and durations by a ratio, and updates one flat range; Option-duplicate clones those notes/chords. That flat array remains a compatibility projection for the existing UI, but it is no longer the only imported representation.

The implemented preservation interface is:

```text
Song.nativeSections: [KlimperSection]?
KlimperSection { fields: [String: NativeJSONValue], children: KlimperSectionChildren }
KlimperSectionChildren = .sections([KlimperSection], metadata)
                       | .clips(NativeJSONValue)
                       | .opaque(NativeJSONValue)
                       | .absent
KlimperSectionPath(indices: [Int])       // sibling indexes at each level
```

Keep section JSON length values and clip JSON untouched in this model. The playback scheduler converts elapsed time using `bpm / 60000 * 0.25 * 10368`, so 10368 stored ticks correspond to four quarter-note beats at the selected BPM. The importer multiplies JSON time numbers by four when creating the clone's quarter-beat projection, including section/note/chord durations and loop bounds; the retained native tree remains in original JSON units. The recursive model query proves the nested note origin and sequential chord placement, although the real-time event-vector producer has not been linked to that query. The flat UI projection remains explicitly separate from the raw tree. Future `wrapInNewSection` work should snapshot selected complete subtrees and parent paths before changing the tree, with exact original/applied snapshots for undo and redo. `moveSection` should use a destination sibling boundary (the observed drop handler increments the final nonempty path component by one) but must leave same-parent index correction, source deletion, and descendant timing shifts behind unresolved policy seams. Resize should be a duration edit command; no native resize implementation or ripple/clip rule is yet established, so the flat prototype's scale-and-ripple behavior is not evidence-based.

### Recursive section data now carried through project save/load

`Song.nativeSections` now stores the imported section tree in root and child order. Each `KlimperSection` keeps unknown section fields as `NativeJSONValue`; its child variant is `.sections`, `.clips`, `.opaque`, or `.absent`. Ordered nested sections are typed recursively, while clip/unknown child objects remain opaque JSON trees so their raw timing and unrecognized fields are not transformed. Numeric JSON values are represented as `Decimal`, avoiding a conversion through beat-space `Double`. `KlimperSectionPath` resolves integer sibling-index paths and rejects out-of-range indices or descent through a clip/opaque section. The new optional Song property uses synthesized `Codable` optional decoding, so v1 `.hsketch` files without `nativeSections` still load.

The normal path is integrated: `KlimperImporter.loadWithWarnings` populates `nativeSections`; `ComposerStore.importKlimper` installs the returned `Song`; `ProjectPersistence` encodes/decodes and validates the recursive count/depth. `SongSection.nativePath` links a projected row to its recursive source path. Name-only edits use that path to change just the native `name` field. The central store mutation boundary marks retained native sections `.projectionOutOfSync` when projected sections, chords, or track notes change; undo/redo restore the corresponding fidelity with the Song snapshot. The optional status keeps older `.hsketch` files decodable; missing historical fidelity remains unknown, so rename synchronization requires a known `.preserved` state. `.preserved` means the original tree remains intact, not that all unsupported native shapes have a complete editable projection. After a structural or clip edit, the saved native tree is explicitly retained as the original imported snapshot and is not represented as current edited content. Tests cover nested ordering, path lookup and variant guards, path-based name edits that preserve raw length/children, unknown payload retention, import→`.hsketch` save/load, and old v1 files without the new fields. Unsupported or missing child content and invalid/nonpositive lengths remain preserved in `nativeSections` but are omitted from the flat timeline projection with a warning.

The recursive tree is the native preservation source; flat `Song.sections` remains the compatibility projection. The section UI now renders the ordered native hierarchy, selects projected leaves by stable index path, and renames only a section's native `name` field. Imported native sections do not expose the prototype's flat move/resize/delete controls. Projection fidelity is visible as preserved, out of sync, or unknown. This task does not add `.klp` export, wrap/move/resize commands, or descendant timing edits. Remaining behavioral gaps include wrap's effective duration after observer dispatch, move relocation, resize side effects, and whether the real-time event producer uses the same recursive model query for note coordinates.

This spec supports lossless semantic retention of the nested section/clip JSON values inside `.hsketch` save/load without hard-coding unsupported timing behavior. ### Recursive note query proves nested coordinate origin

The upstream model query is recovered in `FUN_10002ad90` and `FUN_10002b004`, reached through `FUN_10006fd6c`. Their pseudocode is retained in [`rea-section-recursive-position-evidence-2026-10-16.json`](../../research/rea-section-recursive-position-evidence-2026-10-16.json) with the rest of the 229-record session bundle. Evidence IDs are `ev_f15c55cf3db04491f734c204a5b540233ecf6949374761becb798ce8ad2d319b`, `ev_d02191b5101a11694d9e6a88fbf7c4b509a4a6f855729cb0ae0f6437b59e124b`, and `ev_9a1d4e5ef3f31c0099c0e3e75cbf40e414c2f57df03df9cb6763e5cd3637555e`. The `notes_hitting_range_buffered` callback type is independently visible in RTTI and its closure call operator is `FUN_10002c610` (`ev_531bf704ff9c552f8f27bc3dbe09d5b80c6648a8e9031659bcf59133127206c7`).

`FUN_10002ad90` walks a `vector<Section>` using a `0xa8`-byte stride and keeps a cumulative start. Before querying each child it subtracts that start from the requested range, bounds the child query by the child's `+0x20` length and remaining range, and passes the child into `FUN_10002b004`. After the child returns, it adds the cumulative start to the position field (first qword) of each newly appended result note, advances the cumulative start by the current section's `+0x20` length, and continues. `FUN_10002b004` handles the section's clip variant and per-track note vectors; at another nested-section variant it dispatches back through `FUN_10002ad90`. The same reduction and restoration at each recursive level proves the note coordinate rule: each leaf note's position is local to its containing section, and its song-relative position is the leaf position plus the sum of preceding sibling section lengths at every ancestor level. The importer can therefore project nested notes by accumulating sibling lengths recursively; parent-start-plus-leaf-position is the correct rule for this static model query.

The same `FUN_10002b004` clip-variant branch distinguishes the `ChordTrackHandle` alternative from ordinary track selection (the native `notes_hitting_range_buffered` signature stores `variant<ChordTrackHandle, size_t>`). For the chord-track alternative it walks the ordered `0x40`-byte chord records, queries each chord's voicing-note vector at `record + 0x28` after subtracting the accumulated start, shifts returned note times back by that start, then increments the start by the chord duration at `record + 0x20`. This is direct evidence that chord items are sequential: chord `i` begins at the sum of earlier chord durations within that clip section. Combining this with recursive section traversal gives a model-level chord start of enclosing section start plus prior chord durations. A normal track alternative instead looks up its note vector by track key and does not apply chord-duration accumulation. The `0x28` field is the chord voicing vector corroborated by chord serialization (`FUN_1000108a4`, `ev_28a789c59da99977d9baa06b2a8530d1be5c45d7a5c5018a9a7252d627f00f7b`); duration is emitted from `record + 0x20`.

The corrected importer rule must still honor the existing scale: native JSON time units are multiplied by four to produce quarter-beat coordinates, and all cumulative additions occur after that conversion (equivalently, recursively accumulate native lengths before one final conversion). `FUN_10006fd6c` computes an upper range across root sections and then invokes the recursive visitor; it does not introduce an additional origin. Parent length fields and child ranges are treated as half-open/bounded query windows by the visitor, but that range-query detail should not be mistaken for an editor resize or playback clipping policy.
