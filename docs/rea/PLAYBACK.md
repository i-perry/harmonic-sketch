## ProjectPlayer scheduler trace

The scheduler behavior below comes from decompilation and exact data references in the shipped arm64 artifact. `FUN_1000295e0` obtains `std::chrono::system_clock::now()`, divides its returned count by `1000.0`, subtracts a saved value at receiver offset `+0x160`, calls `FUN_100029860(delta, receiver)`, and stores the new timestamp. `FUN_10002980c` performs the same calculation using a timestamp at `+0x18` and calls the scheduler with the receiver adjusted by `-0x148`.

Both wrappers are referenced from `HighResProjectPlayer` vtable data. The primary table at `0x1009be390` has RTTI pointer `0x1009be3f0` and entries at `0x1009be3a0` onward, including `FUN_1000295e0`; the secondary table at `0x1009be3b8` has offset-to-top `-0x148`, the same RTTI pointer, and entries at `0x1009be3c8` onward, including `FUN_10002980c`. RTTI name data at `0x1009be3f8` identifies `HighResProjectPlayer`. This links the scheduler path to the player class by the vtable layout; the stripped function names remain unnamed. Evidence: vtable bytes `ev_15f365bc937642ac3cc87b33bb2497a08d23b7dc77177f22255826170c7dcefd`; scheduler `ev_496e7b8f281f98e00a985efcc8ec85294abad4586604117036e84ae8eb075032`; wrappers `ev_48e62e8c9fb4677201421b83ee72b9718e88db311ded64893b238173ffd522f3` and `ev_57bee03509767284cd28f631aff319a9eac6b9a72809a28a3dd51f2a84b05a02`.

On each callback, `FUN_100029860` updates a wall-clock base at receiver `+0xe0`, refreshes loop bounds through `FUN_100029c04`, and reads BPM through the callback at `+0xd0` into `+0xd8`. It converts elapsed milliseconds to ticks using double precision and integer truncation:

```text
ticks_per_ms = (bpm / 60000.0) * 0.25 * 10368.0
raw_ticks = trunc(ticks_per_ms * elapsed_ms)
raw_tick_ms = ((raw_ticks / 10368.0) * 4.0 * 60000.0) / bpm
carried_ms = prior_fractional_ms + (elapsed_ms - raw_tick_ms)
carry_ticks = trunc(ticks_per_ms * carried_ms)
carry_tick_ms = ((carry_ticks / 10368.0) * 4.0 * 60000.0) / bpm
fractional_ms = carried_ms - carry_tick_ms
delta_ticks = trunc(raw_ticks) + trunc(carry_ticks)
```

The fractional-millisecond remainder is stored at `+0xe8` between callbacks. Position advances in integer tick units while fractional time carries forward. The app's `PlaybackClock` previously accumulated continuous fractional beats; it now mirrors the observed integer-tick truncation and millisecond carry, using the same calculation order and 2592 ticks per app beat. Derived-vector tests check the 120 BPM sequence `[5, 5, 5, 5, 5, 6]` for six 1 ms callbacks, equivalence to one 6 ms callback, carry across BPM changes, and zero/backward time intervals. This aligns clock advancement only; the reference callback cadence and system clock period remain unestablished. The formula treats 10368 units as a whole note, hence 2592 units per quarter-note beat at the selected BPM; that musical interpretation is derived from the observed factor of four and the BPM conversion. The `system_clock` result is divided by 1000 and then used as milliseconds by this conversion, but the target's clock-period declaration was not established in this trace. Evidence: scheduler dossier `ev_496e7b8f281f98e00a985efcc8ec85294abad4586604117036e84ae8eb075032`.

`FUN_10002a158` advances the cursor at receiver `+0xe` by a nonnegative integer tick delta. It considers note events in the half-open interval `[cursor, cursor + delta)`, schedules eligible note starts through the output callback at receiver `+0x20`, and converts each event's distance from the cursor back to milliseconds as `distance / 10368 * 4 * 60000 / bpm`. It advances the cursor by the full tick delta afterward. Evidence: `ev_6ac319de04d90e59b342aa05f0f8f4c658a335299242db1e49cb78ec8031682b`.

When a callback crosses the loop end at receiver `+0x88`, `FUN_100029860` advances to the boundary, converts the distance to milliseconds, and stops/removes currently playing notes at that boundary offset. If the repeat bit at `+0x69` is set, it resets the cursor to the start at `+0x80` and advances the leftover ticks, passing the boundary offset so post-wrap events retain their timing within that callback. If the bit is clear, it sets the cursor to the end and clears the active bit at `+0x68`. If the cursor is already at or beyond the end at callback entry, it stops notes, sets the active bit from `+0x69`, and resets the cursor to start without advancing the callback delta in that branch. The roles of these two fields are inferred from their branch behavior; their source-level names and initialization from serialized `looping` were not recovered. Evidence: `ev_496e7b8f281f98e00a985efcc8ec85294abad4586604117036e84ae8eb075032`.

Boundary cleanup is implemented by `FUN_10002d68c`: it computes note-off time as the refreshed callback timestamp `+0xe0`, plus the supplied boundary offset, plus the player output offset at `+0x90`; it calls the output callback at `+0x40` and returns true. `FUN_100029ea8` removes active entries whose predicate returns true, so this callback stops and removes each active note. The associated closure type string is `ProjectPlayer::_stop_all_notes_with_offset`. Evidence: callback `ev_32af5323b46a739b009afd31d461cfd78c8c1577a4dfce3957c8c2dd51d73a84`; active-entry filter `ev_6b4ac5379e3355733dc7416d915cd2dff0e75d5c564f20634d8429a9d72dd99d`; closure name `ev_b11c7200bf80402055e3bf1e112ae70a9a85cf628aeffacd7b048be364389a29`.

## Remaining unknowns and prototype implications

The timing scale, event window, loop-boundary wrap/cleanup, chord-preview spacing arithmetic, and effective-velocity gating are now grounded in code. The clone converts its strum control's seconds to ticks using the current tempo, creates events with the recovered 10,368-tick base duration and 162-tick minimum, and normalizes its integer preview velocity to a 0–1 gain before scaling to MIDI velocity. This is an explicit UI adaptation: native player offsets `+0x20` and `+0x28` have not been tied directly to visible controls. The output callback's note-on/off semantics, instrument/string interpretation, and MIDI export selection/timing/quantization remain unresolved. The mapping from persisted `looping` to the two runtime bits is still unknown. The `looping` key has a serializer reference at `0x10000be84`; RTTI-related strings include `polydigm::music::looping` and `polydigm::music::LoopRegion`, but those names do not prove which value initializes runtime byte fields `+0x68` and `+0x69`. No loop behavior change was made. The clone currently folds an elapsed position by modulo in one timer update; the recovered scheduler processes one end boundary and advances leftover ticks once, so large multi-loop overshoot is a known call-site mismatch. It remains uncorrected because the persisted loop-field mapping and reference callback cadence are unknown.

REA used Ghidra's default static analysis. Decompiled output is generated pseudocode, not original source. Indirect calls without resolved targets and runtime behavior remain unknown. Timing implementation: `AudioEngine.swift` and `PlaybackTimelineTests.swift`. The persisted-loop mapping remains unknown. The original release package was signature-verified at `dist/Harmonic Sketch Evidence Parity 2026-10-16.app`; that package predates the responsiveness mitigation below. The playback-only test run passed 34 tests before the later tonal changes; the subsequent combined Swift suite passed 36 tests with no failures.

## Playback position publication fix and runtime verification (2026-10-16)

A controlled diagnostic A/B isolated the publication path. In the baseline build, the main-loop heartbeat continued before and after Play, but the app reached about 96% CPU while emitting beat updates and CUA accessibility reads timed out. With only beat-to-view publication suppressed, Play/Pause accessibility reads returned in about 0.69 seconds and Activity Monitor showed about 0.1% CPU while playing. The main loop was therefore still servicing work; evidence pointed to the high-frequency published beat invalidating too much of the SwiftUI tree rather than an audio-engine or unconditional run-loop deadlock. The baseline and NoBeat trials used an empty project, so these CPU values are diagnostic comparisons, not final performance benchmarks.

The implementation now keeps beat position in a stable `PlaybackPosition` observable object. `ComposerStore.playhead` remains a computed get/set facade, while the transport readout and playhead markers are the only views that observe the high-frequency position object. The composer-wide store no longer publishes each beat. A regression test verifies that changing the position does not emit `ComposerStore.objectWillChange`.

Runtime acceptance used the diagnostic-gates-removed, position-split build with a disposable copy of `qa/smoke.hsketch` at `/private/tmp/klimper-playback-smoke-2026-10-16.hsketch` (one note, one chord). CUA reported Play→Pause within 0.67 seconds; the displayed position advanced from 0.8 to 5.5. Editing tempo to 140 BPM while playing returned within 0.72 seconds, and a second run advanced from 0.9 to 11.4. Pause returned the control to Play and Stop reset the position to 0.0. Activity Monitor showed the isolated post-fix app at 3.3% CPU during playback and 7.9% after Stop. These measurements are a substantial improvement over the earlier beat-publishing baseline, although the app-scene setup and sampling intervals were not a controlled benchmark. The session snapshot remains unchanged at SHA-256 `0a78ba8db1e1eeeb4ec45211b2e7fc3fba228ee739b0e5d1ce5438a3f5527bd1`.


## Chord preview event-window dispatch

The timer callback closure operator `FUN_10002fa7c` runs two passes over a range of 24-byte entries (`0x18` stride). Each entry's first two 64-bit fields define a start and an end as `field0` and `field0 + field1`; the last eight bytes are passed to an event handler as two 32-bit values at offsets `+0x10` and `+0x14`. The first pass filters entries whose computed end is in `[position, position + tick_delta)`. The second filters entries whose start is in that same half-open interval. These are direct decompiler observations; interpreting the first two fields as start and duration follows from the comparison and addition, and the callback payload's musical meaning is not identified. Evidence: `ev_6d3c790bd69b51a72ca3c9f976a0104d7f9813ab894aa9b9f1800f6afebb6c50` (`FUN_10002fa7c`), `ev_b24256e813f976620af0ce58720b738cf78d601bbff2b3642434c7fe71d460b4` (filter and append in `FUN_10002fee0`), `ev_320326a5f9a8626b0efe19e199881130b7c7b65dd8b28731e27759246646ee4d` (end-boundary predicate), and `ev_713710b1ed7d08c4d97b6b2fc0d76c53b51e9a03fedacafbda128c5c54da227c` (start-boundary predicate).

Within each pass, retained entries are appended in their original range order. The callback performs the end-boundary pass before the start-boundary pass, so same-tick end handlers precede same-tick start handlers. The end-boundary closure is `FUN_1000303d0`; the start-boundary closure is `FUN_1000300d0`. The start handler calls an indirect callback using the two 32-bit payload words and inserts a map entry keyed by the first payload word. The end handler calls a different indirect callback with the first payload word, then removes a map entry using that same field. These effects are observed; whether the callbacks correspond exactly to MIDI note-on/note-off and what the payload words encode is not proven by these functions alone. Evidence: `ev_7a6b09c7e80c5aa166a00f0747681e234533720873ccbb7a5661308e604cb45b` (end handler), `ev_3796dba6df293b4f036dfb1381256cd3ee06ad907cd5a031d911e0aac53150fb` (start handler), and `ev_c1c79f82f94674a92592ea38079e25df050de2da4ab1b215144cefe6abfc6e20` (range append).

The vector producer is `FUN_100030dc0`, called by `FUN_1000309b0` before the generated range is sorted by `FUN_1000316c4` and installed at player offset `+0x1c0`. It emits one base-pitch event followed by an event for each chord-map entry. Map tone keys are read as 16-bit values and added to the base pitch. For event index `i`, it computes `offset_i = trunc((spacing / 10368.0) * i * 10368.0)`, where `spacing` is read from player offset `+0x20`; start is increased by that offset and duration is reduced from `0x2880` (10368 ticks) by the same offset, with a 162-tick minimum. This recovers the per-entry spacing arithmetic and limit from the producer, but does not prove that the `+0x20` field is directly initialized from the visible `strumming` setting. The event's float payload is the product of the value returned by the Project getter at `+0x30` and the float at player offset `+0x28`; the next paragraph traces the getter to `effective_velocity`. Evidence: `ev_aa96d15bcca5d5eec4609f7a156b7d627a31e758c0efa5381266771e9f16b37c` (event producer), `ev_c947d219ebe4d93237ee9c48e3922c0c9053ce4f701853e68b4a02254b998dcc` (vector construction, installation, and reset), and `ev_eaf5da1f61933e488108c46351ee35f87f0046ab0dff1f453ed3d92a4e04bdbc` (sort implementation).

Applying the timer's tick-to-time conversion, a spacing value of `S` ticks corresponds to `S * 4 * 60000 / (10368 * BPM)` milliseconds between adjacent event starts, assuming the preview timer's rate field is the same BPM used by its callback formula. Before the 162-tick minimum duration applies, each event's computed end is at tick 10368 because its start offset is subtracted from the base duration by the same amount. The event end handler runs at that computed boundary and removes the associated map entry; the downstream output callback's audible note-off behavior is not established. Evidence: preview producer `ev_aa96d15bcca5d5eec4609f7a156b7d627a31e758c0efa5381266771e9f16b37c`; timer tick conversion `ev_7885d97a72b1b5e82e1d56ac14d4f00ce66e7a88896ae69691d1d69d9995a728`.

When a generated sequence is nonempty, the producer normalizes the last pitch class modulo 12; if it is less than the integer reached through player offset `+0x300`, it adds 12 to every event pitch. This is an observed transposition rule; the pointed-to integer's source-level meaning is not established. The generated entries start as the base pitch followed by ascending chord-map keys, but the subsequent sort compares `start + duration` and is not stable. Thus generator order is known, while the final relative order of equal-end entries is not guaranteed by this trace. Evidence: `ev_e8aa3785202f6fe1c0c58dcef50f78d7800c880e035c7b6b43e18770ceac1928` (producer's pitch adjustment and event fields), `ev_83b520a2c060d1c600237fece3afff793cdc239e96717e5379fff1aa09267747` (getter path), and `ev_77b65ab356f7aa851c3422436572fbe44801b57fb5b98138d7c571d153e4dbef` (sort comparator).

The velocity path is also resolved. `FUN_1000309b0` obtains a float from the Project `getIf` callback, whose type-erased target is `polydigm::music::effective_velocity`; its invoke slot leads to `FUN_100033010`. Depending on the callable's captured selector flag, that function either uses the Song record directly or finds a Track whose `+0x40` identifier matches the captured identifier. It reads the selected record's raw float and two flag bytes at `+0x08`, then writes either that float or zero. Precisely, output is the selected record's raw float when the low flag byte is zero and either the aggregate flag is false or the high flag byte is nonzero. The aggregate flag is the Song byte at `+0x09` OR any Track byte at `+0x09`. The source-level meanings of these flags remain unknown. The event producer multiplies this result by the float at player offset `+0x28` and writes it into every chord-event payload. This path shows no curve or clamp. The clone uses its visible integer velocity as the gain; this is a compatibility choice, not a recovered binding to the native player field. Evidence: `ev_6ed7a657299ef9dadc75270b35c5ae529a9eeb4e2c81f9593d587440e78d6a5b` (callable type), `ev_ac50da91a22c42271a009e8f6920d119cc5c3855163fedcb76218c2a53517c18` (invoke vtable containing `FUN_100033010`), `ev_0abfe782c339d9c0f55a99a92858dc65ce91f86d4ecd74631f4c9e6d7eb8621b` (callable implementation), `ev_24bb55a1571bb9e9422acdf83e8c55505fbdb31d658f293cfac1ae540d992e40` (conditional Track lookup), `ev_83b520a2c060d1c600237fece3afff793cdc239e96717e5379fff1aa09267747` (Project getter path), and `ev_e8aa3785202f6fe1c0c58dcef50f78d7800c880e035c7b6b43e18770ceac1928` (velocity payload construction).
